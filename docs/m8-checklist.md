## 1. 你要先放告示牌（約一分鐘）

在**任何一個創造模式世界**（不要用語料地圖，找個新的平坦世界最省事）：

* 放 **5 面一般告示牌**（`oak_sign` 之類）
* 放 **4 面吊掛告示牌**（`oak_hanging_sign` 之類）

**正反面都要空白**——放下去按 Esc 直接離開編輯畫面就是空白的。排成一列、面朝同一邊
最好認。存檔離開。

> **為什麼要你手動放**：這個工具從來不碰方塊，只碰方塊實體裡的文字。要它生成一串
> `/setblock` 就得猜 1.21.11 的方塊實體 NBT 語法，猜錯的症狀是「進遊戲什麼都沒出現」
> ——白跑一趟。改寫既有告示牌走的是我們自己測過的寫入路徑。

## 2. 匯入並產生校準告示牌

```
.venv\Scripts\python -X utf8 -m mcmt.cli sandbox import "<...>\saves\<你的世界>" --name calib
.venv\Scripts\python -X utf8 tools\calibrate_font_widths.py "sandbox/calib"
```

腳本會印出**每一面告示牌的 `/tp` 座標與它上面的四行是什麼**。把那份輸出留著，進遊戲
時要對照。

一面告示牌 4 行、正反共 8 行，所以 9 面牌放得下 52 行階梯 + 16 行校準板。

### 兩種量測，一次做完

| | 放什麼 | 你要回報什麼 | 抓到的是 |
|---|---|---|---|
| **階梯** | 第 N 行放 N 個同樣的字 | 「最後一行完整顯示的是第幾行」 | **臨界點** |
| **校準板** | `iiiiiiiiii`、`中中中中中`、粗體 `MMMMMMMMMM`… | **截圖** | **精確值** |

兩種都做的理由：單靠階梯，如果 ASCII 寬度表本身記錯了（`i` 到底是 2px 還是 3px），
你不會知道——推出來的預算會整個偏掉而且看起來很合理。校準板上每一條的預期寬度都
算得出來，對不上就是表錯了。

## 3. 進遊戲

1. 把 `sandbox\calib` **整個資料夾複製**到 `%APPDATA%\.minecraft\saves\`
   （工具永不自動複製回去——那是你的決定，CLAUDE.md §1.1）
2. 用 **1.21.11** 開啟，`/gamemode spectator`
3. 照腳本印的 `/tp` 一面一面看過去

### 要回報的四個數字

| # | 問題 |
|---|---|
| 1 | 一般告示牌：ASCII 階梯**最後一行完整顯示**的是第幾行（第幾個 `M`） |
| 2 | 一般告示牌：CJK 階梯最後一行完整顯示的是第幾行 |
| 3 | 吊掛告示牌：ASCII 階梯最後一行完整顯示的是第幾行 |
| 4 | 吊掛告示牌：CJK 階梯最後一行完整顯示的是第幾行 |

「完整顯示」= 最後一個字沒有被切掉一半、也沒有超出木板範圍。

**另外對每一種告示牌的校準板各截一張圖**（正對著、盡量近）。那八行是精確值的來源。

> 校準前的猜測是 sign 90px / hanging 60px / CJK 9px，也就是預期答案 **15 / 10 / 10 / 6**。
> **2026-08-21 量到的就是這四個**——所以那不是白跑：它證實了 [遊戲實測 M11-2]
> 「7 個 CJK 字被截掉」不是碰巧對上，`hanging_sign` 因此從 `[待驗]` 升成 `[遊戲實測]`。

## 4. 回填

```
.venv\Scripts\python -X utf8 tools\calibrate_font_widths.py --record ^
    --sign-ascii-max 15 --sign-cjk-max 10 ^
    --hanging-ascii-max 10 --hanging-cjk-max 6 ^
    --sign-bold-shown 10 --hanging-bold-shown 8
```

（上面就是 2026-08-21 那次實際用的指令。）

腳本會：

* 把預算取 `臨界字數 × 字寬` 的**下界**（寧可少報空間，也不要答應一個其實放不下的字數）
* 從兩種告示牌各推一個 CJK 寬度的**區間**再取交集——不是各算一個整數再要求相等。
  階梯只給得出區間，硬要相等會把一組其實一致的觀察判成錯誤，而假警報比沒有檢查更糟
* 把你回報的原始觀察一起寫進 JSON，讓推導過程之後查得到
* 交集是空的就**拒絕回填**，請你改用校準板的截圖直接量（`--cjk-advance N`）
* 粗體那兩個數字（校準板第 7 行看得到幾個 `M`）把 `bold_extra` 釘死。**三個觀察要
  一起解**：只看 ASCII 區間的話，`e=2` 也會留下來——它要求吊掛預算落在 64..65px，
  而同一面「6 個中文字進得去、7 個不行」要求 < 63px，兩者其實互斥，分開檢查看不出來

回填之後**跑一次 pytest**。`tests/unit/test_width.py` 有幾條測試綁著目前的數字，
它們變紅是預期的——**要照新的量測值改，不是把測試放寬**。

最後把結果寫回 `SPIKE_RESULT.md`（證據等級 `[遊戲實測]`）與 `docs/STATUS.md`。
單人開發沒有第二個人會提醒你這一步。

## 5. legacy chunk 的 `CustomName`（✅ 2026-08-21 完成）

**這一項當時卡著 9,579 個節點。** [實測 2026-08-21] `Arena of Darkness` 的
CustomName occurrence 全部是舊世代（DV 3700 的 JSON 純量 9,259 個 + DV 3465 的
JSON 物件 320 個，native 的 **0** 個），全數以 `untested_write_shape` 排除——
也就是這張地圖的 CustomName 一個都寫不出去。

重跑的方式（換版本時用）：`tools/customname_probe.py --generation legacy --find`
找一個世代對得上、容器夠多的 chunk，再對它跑一次；2026-08-21 用的是
`region r.-3.1.mca` 的 chunk 235。把世界複製到 `.minecraft\saves\` 用 1.21.11 開啟，
`/gamemode spectator`，然後開這三個箱子看標題：

| 變體 | 寫進去的 | `/tp` | 顯示什麼代表什麼 |
|---|---|---|---|
| **A** JSON 純量 | `"A 純量成功"` | `/tp @s -1353 129 625` | 顯示「A 純量成功」→ **保留原形狀的 in_place 可行**，9,579 個節點解開 |
| **B** JSON 物件 translate key | `{"translate":"mcmt.test.customname"}` | `/tp @s -1353 127 625` | 顯示「自訂名稱翻譯成功」→ 更好：legacy 可以走 translate key，一份存檔支援多語言 |
| **C** 裸字串（非 JSON） | `C 裸字串成功` | `/tp @s -1353 129 626` | 顯示「C 裸字串成功」→ DataFixer 對非 JSON 字串是寬容的 |

三個都顯示成字面亂碼 → 維持排除，而且我們知道那不是保守過頭。

> 這張地圖自己帶了一個 **131 MB 的 `resources.zip`**，腳本是**合併**進去的（既有
> 329 個條目一個都不動），不是覆蓋。M4 第一版覆蓋掉它、被 `BackupSet` 接住過。

### 2026-08-21 的結果

| 變體 | 開箱子看到 | 結論 |
|---|---|---|
| **A** JSON 純量 | 「A 純量成功」 | **成立** |
| **B** JSON 物件的 translate key | 「自訂名稱翻譯成功」 | **成立**，資源包解得開 |
| **C** 非 JSON 的裸字串 | **「大型儲物箱」** | **失敗，欄位整個被丟掉** |

**C 是最重要的一個，而且它是反面的**：顯示的是原版預設容器名，代表 DataFixerUpper
沒能解析那個字串、整個欄位被丟棄。所以在舊世代換掉節點的形狀會**悄無聲息地弄丟
別人地圖上的名字**——「保留既有形狀」不是保守，是唯一不會壞事的選擇。

落地與完整記錄見 `SPIKE_RESULT.md`「M8 + legacy CustomName 遊戲實測」⑤。
